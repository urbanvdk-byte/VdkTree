1. ЗАДАЧА
Пользователь распорядился назначить уже зарегистрированную учётную запись с логином savenko администратором и реализовать полноценный раздел «Пользователи» для администраторов VdkTree. В версии v1.0.2 администраторские права выдавались только через ручной SQL в BotHost. Не было управления участниками, ролями и блокировками через веб-интерфейс.

2. СОСТОЯНИЕ ДО ИСПРАВЛЕНИЯ
В PostgreSQL уже существовала таблица vdktree.users, связанная с подписанным MAX-аккаунтом. Пользовательское имя login имело уникальный регистронезависимый индекс. Роли user/moderator/admin хранились в колонке role. Сессии хранились отдельно в vdktree.sessions и проверялись по JWT-подобному токену (фактически случайный bearer token с SHA-256), а исходные пароли — как scrypt-хеши. Отдельных полей блокировки пользователя и времени последнего входа не было.

3. НАЗНАЧЕНИЕ ADMIN ДЛЯ SAVENKO
Прямого соединения из инструментов ChatGPT с живой базой BotHost нет; поэтому не утверждается, что роль уже изменилась в рабочей базе. Вместо опасного бессрочного правила автоматического повышения добавлена строго однократная миграция в users_admin_api.setup():
- Во время первого запуска v1.0.3 в BotHost проверяется только существующая на тот момент запись с login=savenko без учёта регистра.
- Если запись есть, не заблокирована и роль ещё не admin — role обновляется на admin и создаётся аудит bootstrap_admin.
- Результат фиксируется в vdktree.admin_bootstrap_history с маркером v1.0.3:existing-login:savenko.
- Если запись уже admin, отмечается already_admin; если blocked, отмечается blocked; если нет такой записи, отмечается not_found.
- После первого выполнения повторные старты не меняют роль savenko. Новая регистрация с таким логином после миграции не получит повышенных прав.
- Транзакция сериализована через pg_advisory_xact_lock для защиты от одновременного запуска процессов.
- Указанное изменение будет применено только после обновления BotHost из GitHub main и запуска новой версии.

4. АРХИТЕКТУРА СЕРВЕРА
Создан users_admin_api.py с APIRouter(prefix=/api/v2/admin/users).
Доработана схема PostgreSQL vdktree:
- ALTER TABLE users ADD COLUMN IF NOT EXISTS is_blocked BOOLEAN NOT NULL DEFAULT FALSE.
- ALTER TABLE users ADD COLUMN IF NOT EXISTS last_login_at INTEGER.
- CREATE TABLE admin_user_audit: действие, target_id, actor_id, данные до/после, причина, время.
- CREATE TABLE admin_bootstrap_history: однократные административные миграции.
Чужая схема public PostgreSQL не изменена. Удалений учётных записей или их растений не выполняется.

API доступно только текущей серверной роли admin:
- GET /api/v2/admin/users — список, поиск имени/логина/MAX ID, фильтры по роли и блокировке, пагинация по 30 (максимум 100), сводные счётчики, статистика объектов/замечаний, дата регистрации и входа.
- GET /api/v2/admin/users/{id} — данные выбранного участника и число активных сеансов.
- GET /api/v2/admin/users/{id}/history — журнал всех админских действий с исполнителем.
- PATCH /api/v2/admin/users/{id} — назначение user/moderator/admin и блокировка/разблокировка; причина обязательна, запись аудита.
- POST /api/v2/admin/users/{id}/revoke-sessions — завершение действующих сеансов с причиной.
- POST /api/v2/admin/users/{id}/reset-credentials — очистка прежнего логина и хеша пароля, завершение сеансов; после этого новый логин/пароль можно создать только через MAX.
API не позволяет удалить пользователя и потерять связь с объектами.

5. БЕЗОПАСНОСТЬ И ЗАЩИТЫ
- Проверка роли на сервере в admin_only; скрытие кнопок JS не даёт административных прав.
- Поля role валидируются по строгому набору user/moderator/admin.
- Администратор не может менять собственную роль, блокировать себя, сбрасывать свой пароль или завершать все свои сеансы через административный API.
- Нельзя понизить или заблокировать последнего активного администратора; действия сериализуются транзакционной блокировкой.
- При блокировке пользователя удаляются его сессии и запрещаются новые входы через MAX и по паролю, а также выдача новой браузерной сессии через одноразовый код MAX.
- auth_backend.current_session читает is_blocked из PostgreSQL при каждом запросе, поэтому права и блокировка применяются сразу.
- При успешной авторизации теперь обновляется last_login_at.
- В API выдаются только безопасные поля. password_hash, токены и другая секретная информация не возвращаются.
- Вся передача SQL-параметров выполняется через привязку параметров, поиск экранирует LIKE-шаблоны.

Собственная карточка администратора защищена от ошибочного редактирования.

9. ПУБЛИКАЦИЯ И ПРИЁМКА
После зелёных тестов PR №7 объединяется с main. Для применения в BotHost пользователь обновляет код бота из ветки main с полной пересборкой и перезапуском. DATABASE_URL и MAX_BOT_TOKEN остаются прежними.
После запуска GET /api/health должен показать version=1.0.3 и database=postgresql. Миграция savenko выполнится один раз, если запись уже существовала. Результат проверяется из защищённого SQL-редактора по инструкции inventory/USERS_V103.md; затем после повторного входа в веб-приложение должна появиться кнопка «👥 Пользователи».
Публикация GitHub сама по себе не изменяет рабочую базу BotHost. Реальная проверка после обновления остаётся за пользователем.
