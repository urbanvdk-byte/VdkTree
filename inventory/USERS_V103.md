# VdkTree v1.0.3 — раздел «Пользователи»

## Первое назначение savenko

При первом запуске v1.0.3 на BotHost выполняется **однократная миграция**:

1. Проверяет уже зарегистрированный логин **savenko** без учёта регистра в таблице vdktree.users.
2. Если запись найдена и не заблокирована, ставит роль admin и добавляет запись в admin_user_audit.
3. Сохраняет результат в admin_bootstrap_history. Возможные результаты: promoted, already_admin, blocked, not_found.
4. Повторный запуск миграцию не повторяет. Если savenko будет понижен позднее — повторного повышения не будет.
5. Если учётной записи пока нет, результат not_found фиксируется окончательно. Тот, кто зарегистрирует логин savenko позже, автоматически администратором не станет.

Это безопаснее постоянного правила «любой savenko — админ». Таблицы PostgreSQL public.users не меняются. Вся авторизация по-прежнему основана на подтверждённой учётной записи MAX и реальной базе vdktree.users.

**Важно:** GitHub и автоматические тесты не изменяют рабочую базу BotHost. Миграция выполнится только после обновления сервера из main и его первого запуска v1.0.3.

Для проверки результата на BotHost, в SQL-редакторе PostgreSQL:

    -- НАЧАЛО КОПИРОВАНИЯ — PostgreSQL
    SELECT login, role, is_blocked
    FROM vdktree.users
    WHERE lower(login) = 'savenko';

    SELECT marker, outcome, executed_at
    FROM vdktree.admin_bootstrap_history
    WHERE marker = 'v1.0.3:existing-login:savenko';
    -- КОНЕЦ КОПИРОВАНИЯ

Если результат not_found или blocked, администраторскую роль можно назначить вручную после проверки записи и MAX ID владельцем:

    -- НАЧАЛО КОПИРОВАНИЯ — PostgreSQL
    SELECT id, max_id, display_name, login, role, is_blocked
    FROM vdktree.users
    WHERE lower(login) = 'savenko';

    UPDATE vdktree.users SET role='admin'
    WHERE lower(login)='savenko' AND is_blocked=FALSE
    RETURNING id, max_id, display_name, login, role;
    -- КОНЕЦ КОПИРОВАНИЯ

## Как открыть раздел

Откройте https://urbanvdk-byte.github.io/VdkTree/, войдите через MAX или по логину и паролю. Убедитесь, что в правом верхнем углу v1.0.3. После первого назначения роли обновите страницу или повторите вход для перечитывания статуса из PostgreSQL.

У администратора появятся кнопки «Модерация», «Импорт Excel/CSV» и новая «👥 Пользователи».

## Что доступно администратору

- Список всех зарегистрированных участников: имя MAX, логин, MAX ID, роль, статус, дата регистрации и последнего входа, число объектов и замечаний.
- Поиск по имени, логину и MAX ID; фильтрация по роли и блокировке; постраничная загрузка по 30 человек.
- Изменение роли: user (пользователь), moderator (модератор), admin (администратор). Нужны подтверждение и обязательная причина.
- Блокировка и разблокировка. При блокировке все действующие сеансы завершаются. Новые входы через MAX или пароль запрещены.
- Принудительное завершение всех сеансов выбранного участника.
- Сброс логина и пароля другого участника, с завершением его сеансов. Восстановление — повторным входом через MAX и созданием новой пары.
- История действий администратора с причиной, прежними и новыми правами, исполнителем и временем.

## Защитные ограничения

- Все API раздела доступны только роли admin по текущей серверной сессии. Отображение или скрытие кнопки в браузере не является проверкой прав.
- Администратору запрещено изменять свою роль, блокировать самого себя и сбрасывать собственную пару логин/пароль.
- Нельзя понизить или заблокировать последнего активного администратора.
- Изменения ролей начинают действовать немедленно на сервере; для обновления кнопок открытой страницы может потребоваться перезагрузка.
- Пользователи не удаляются: блокировка сохраняет привязанные растения, замечания и журнал истории.
- История изменений сохраняется в PostgreSQL в схеме vdktree.

## Проверки и эксплуатация

- CI PostgreSQL 16: перед запуском приложения создаётся существующий savenko, проверяется однократное повышение, роли, поиск, ограничения, блокировка, восстановление и аудит.
- Docker проверяется также с конфликтующей таблицей public.users(id INTEGER), чтобы не повторить сбой v1.0.1.
- Строки DATABASE_URL и MAX_BOT_TOKEN остаются только в переменных BotHost.
- Версия API /api/health после обновления должна быть 1.0.3. Интерфейс показывает v1.0.3.
- Полная глава разработки хранится в Daily/VdkTree0017.

Без обновления кода и перезапуска BotHost реальная роль savenko останется прежней, даже если GitHub уже показывает v1.0.3.
